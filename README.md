## สถานะส่งมอบ

ชุดนี้ประกอบด้วยหน้าเว็บที่ทดลองใช้งานได้ โค้ดฐานข้อมูล Supabase พร้อม RLS, Edge Function, Apps Script สำหรับ Drive/Sheets/อีเมล, GitHub Actions และการทดสอบอัตโนมัติ ไม่มีคีย์จริงของหน่วยงานบรรจุอยู่ในชุดนี้ มีสคริปต์สร้าง admin ครั้งแรกด้วยรหัส 123456 ตามที่กำหนด แล้วบังคับเปลี่ยนรหัสก่อนเปิดข้อมูล

โหมดสาธิตใช้ชื่อสมมติ 21 คนจาก 7 สถานศึกษาและเก็บใน localStorage เท่านั้น ไม่ใช่ข้อมูลหน่วยงานจริง อย่าใส่ข้อมูลส่วนบุคคลจริงในโหมดสาธิต เมื่อยังไม่ตั้ง config.js ปุ่มเข้าสู่ระบบจริงจะยังใช้งานไม่ได้ ต้องติดตั้ง Supabase และ Google services ตามขั้นตอนด้านล่างก่อน

ตรวจ syntax JavaScript และการทดสอบตรรกะ/ลายเซ็นได้ในสภาพแวดล้อมพัฒนา รวมถึงทดสอบ schema/migration, transaction และ RLS ด้วย PostgreSQL ผ่าน PGlite โดยจำลอง Supabase Auth ยังไม่ได้เชื่อมทดสอบกับ Supabase ของหน่วยงานจริง, Google authorization/quotas, GitHub Pages จริง, การโหลด CDN และหน้าจอในเบราว์เซอร์ เนื่องจากไม่มีบัญชีและการเชื่อมต่อบริการเหล่านั้น จึงต้องทำ acceptance test ก่อนเปิดใช้ข้อมูลจริง

## เริ่มต้นสำหรับผู้ติดตั้ง

คู่มือนี้เป็นเอกสารผู้ดูแลสำหรับติดตั้งระบบ แยกจากหน้าใช้งานบุคลากร หน้าเว็บไม่มีคำอธิบาย Supabase หรือขั้นตอนพัฒนาแทรกอยู่ในแบบฟอร์ม

เตรียมบัญชี GitHub, บัญชี Supabase และ Google Workspace ของหน่วยงาน พร้อมเครื่อง Windows/macOS ที่ติดตั้ง Node.js LTS, Git และ Python 3 สำหรับจัดแพ็กเกจดาวน์โหลด หากใช้ Windows เปิด PowerShell ในโฟลเดอร์ที่แตกไฟล์ HRVec-Andaman2 แล้วตรวจ `node --version`, `git --version`, `python --version` หากคำสั่งใดไม่พบให้ติดตั้งและเปิด terminal ใหม่ก่อนดำเนินการ

ไฟล์ที่ต้องใช้: `dist` คือหน้าเว็บ, `supabase/schema.sql` คือคำสั่งสร้างฐานข้อมูล, `supabase/functions/hr-bridge` และ `hr-accounts` คือโค้ดเชื่อมไฟล์และจัดการบัญชี, `scripts/bootstrap-admin.mjs` คือสคริปต์สร้างผู้ดูแลครั้งแรก, `apps-script/Code.gs` และ `appsscript.json` คือโค้ดฝั่ง Google ไฟล์ Excel แม่แบบอยู่ใน `dist/HRVec-Andaman2-Personnel-Template.xlsx`

**หากติดตั้งรุ่นเดิมแล้ว:** สำรองข้อมูลและโค้ดก่อน อัปเดตตามลำดับต่อไปนี้ใน SQL Editor ของโครงการเดิม จากนั้นอัปเดตไฟล์ใน `dist` โดยเก็บค่าจริงใน `dist/config.js` ไว้ **ไม่ต้องรัน schema.sql ทั้งไฟล์ซ้ำ**

1. หากยังไม่เคยอัปเดตเป็นรุ่น 1.2 ให้รัน `supabase/migrations/20261020_education_certificate.sql`
2. หากยังไม่เคยอัปเดตเป็นรุ่น 1.4 ให้รัน `supabase/migrations/20261020_privacy_overview.sql`
3. หากยังไม่เคยอัปเดตเป็นรุ่น 1.5 ให้รัน `supabase/migrations/20261020_majors_certificate_import.sql`
4. รัน `supabase/migrations/20261020_personnel_change_review.sql` สำหรับรุ่น 1.6 ผู้ที่ใช้รุ่น 1.5 ใช้เฉพาะไฟล์นี้
5. รัน `supabase/migrations/20261020_managed_accounts.sql` สำหรับรุ่น 1.7 ผู้ใช้รุ่น 1.6 ใช้เฉพาะไฟล์นี้
6. อัปเดต `dist` โดยเก็บ config.js ของหน่วยงาน อัปเดตและ Deploy `hr-bridge` และ `hr-accounts` ใหม่ และแก้ Apps Script พร้อม Deploy New version เพื่อให้สำรองประวัติใหม่และตรวจบุคลากรที่ลบแล้วได้ครบ
7. ผู้ติดตั้งใหม่รัน `supabase/schema.sql` เพียงไฟล์เดียว ซึ่งรวมทุก migration แล้ว ไม่รัน schema ทับโครงการเดิม
8. ตรวจรับด้วยบัญชี admin และบุคลากรคนละบัญชี ก่อนเปิดให้เขียนข้อมูลหลังอัปเกรด รุ่นนี้บังคับแก้ทะเบียนผ่าน RPC ตรวจ revision จึงต้องอัปเดตฐานข้อมูลและหน้าเว็บพร้อมกัน

## สิ่งที่เพิ่มในรุ่น 1.7

- แอดมินกำหนดชื่อผู้ใช้และรหัสผ่านเริ่มต้นจากหน้า **จัดการบัญชี** ครบทั้ง 7 วิทยาลัย มีรายการพร้อมบัญชี/ยังไม่สร้างบัญชี รีเซ็ตรหัส พักบัญชี และเปิดใช้งานใหม่
- ติดตั้งใหม่สร้างชื่อผู้ใช้ **admin** รหัสเริ่มต้น **123456** ด้วยสคริปต์ฝั่งผู้ติดตั้ง บัญชีนี้มีอยู่จริงใน Auth ระบบให้เปลี่ยนรหัสก่อนเปิดข้อมูล ไม่ตรวจรหัสด้วยข้อความคงที่ในหน้าเว็บ
- บัญชีใหม่และบัญชีที่รีเซ็ตต้องเปลี่ยนรหัสส่วนตัวก่อนเริ่มงาน รหัสใหม่อย่างน้อย 8 ตัวอักษร มีตัวอักษรและตัวเลข ไม่เกิน 72 ไบต์ และต่างจากรหัสเดิม
- รหัสผ่านไม่เก็บใน personnel, profiles, Excel, Google Sheets, audit log หรือ localStorage รหัส Auth ถูกจัดเก็บโดยระบบยืนยันตัวตน แอดมินกำหนดใหม่ได้และไม่เปิดดูรหัสเดิม
- ตรวจการเปลี่ยนรหัสครั้งแรกที่ทั้งหน้าเว็บ RLS และ Edge Functions ไม่สามารถข้ามด้วยการเรียก RPC เอง เซสชันที่เกิดก่อนรีเซ็ตหรือพักบัญชีถูกปฏิเสธแม้ใช้ refresh token เดิม
- หน้า **ข้อมูลของฉัน** มีปุ่ม แก้ไขข้อมูล / ขอลบข้อมูล / ประวัติของฉัน บุคลากรอ่านและแก้ไขได้เฉพาะข้อมูลที่ตนมีสิทธิ์
- บุคลากรส่งคำขอลบพร้อมยืนยันเลขที่ตำแหน่งและเหตุผล แอดมินพิจารณาจากเมนู **คำขอลบข้อมูล** อนุมัติแล้วจึงย้ายรายการไป **รายการที่ลบ** และกู้คืนได้
- ถ้าข้อมูลเปลี่ยนหลังส่งคำขอ จะอนุมัติคำขอรุ่นเก่าไม่ได้ ให้ไม่อนุมัติพร้อมเหตุผลและให้ผู้ขอส่งใหม่ ข้อมูลไม่ถูกลบทับโดยอัตโนมัติ
- บัญชีเดิมหลังอัปเกรดยังคงรหัสที่ใช้อยู่ สคริปต์ bootstrap ปฏิเสธการรันซ้ำเมื่อมี admin อยู่แล้ว ไม่รีเซ็ตบัญชีเดิมกลับเป็น 123456

**ผลตรวจรุ่น 1.7:** Node 75 รายการผ่าน และ PostgreSQL ผ่าน PGlite ตรวจบัญชีก่อนเปลี่ยนรหัส เซสชันเก่า สิทธิ์ของฟังก์ชัน การผูกบัญชี คำขอผิดเจ้าของ อนุมัติลบ การแก้ข้อมูลชนกัน อัปเกรดระบบเดิม และรัน migration ซ้ำ ยังต้องตรวจบริการจริงกับบัญชีหน่วยงานและหน้าจอเบราว์เซอร์ก่อนเปิดใช้

## สิ่งที่เพิ่มในรุ่น 1.6

- เพิ่ม **เปิดแฟ้ม / แก้ไข / ลบ / ประวัติ** ในแถวของบุคลากร เลือกสถานศึกษาเพื่อทำงานทีละแห่งได้
- ก่อนเพิ่มหรือแก้ไข แสดงค่าเดิมเทียบค่าใหม่ รวมใบรับรองที่เพิ่มพร้อมกัน ย้อนกลับไปแก้ร่างได้ โดยยังไม่บันทึกจนกดยืนยัน
- การแก้ไขต้องระบุเหตุผล 5–1,000 ตัวอักษรและติ๊กยืนยันตรวจข้อมูล ทั้ง admin และบุคลากรที่แก้ข้อมูลติดต่อของตน
- ก่อนลบหรือกู้คืน แสดงชื่อ เลขที่ตำแหน่ง และสถานศึกษา ให้กรอกเลขที่ตำแหน่งซ้ำและระบุเหตุผล การลบเป็น soft delete ไม่มีคำสั่งลบถาวรจากหน้าเว็บ
- เมนู **รายการที่ลบ** อยู่ในกลุ่ม admin กรองตามสถานศึกษา ค้นหา อ่านประวัติ และกู้คืนได้ เอกสาร/ใบรับรอง/บัญชีที่ผูกยังเก็บไว้ เลขที่ตำแหน่งและ user_id ยังสงวนอยู่ จึงไม่สร้างซ้ำแทนการกู้คืน
- รายการที่ลบไม่นับภาพรวม รายงาน ใบรับรอง และเอกสารรอตรวจ บัญชีบุคลากรเจ้าของรายการที่ลบจะอ่านหรือแก้แฟ้มเดิมไม่ได้จนกู้คืน การลงชื่อเข้าใช้บัญชีเดิมไม่ได้ถูกยกเลิกอัตโนมัติ
- ทุกการแก้ไข ลบ กู้คืน ส่ง `expected_revision` จากตอนเปิดฟอร์มไปตรวจใน transaction ที่ล็อกแถว หากมีผู้อื่นแก้ก่อน จะปฏิเสธและไม่เขียนทับ ให้กด ยกเลิกร่างและโหลดใหม่ แล้วเปิดรายการตรวจอีกครั้ง
- เพิ่ม `personnel_changes` เก็บการสร้าง แก้ไข ลบ กู้คืน ค่าเดิม/ใหม่ ผู้ดำเนินการ เวลา เหตุผล และ revision admin อ่านรวมและบุคลากรอ่านเฉพาะของตน เก็บลายนิ้วมือของรูปเพื่อระบุว่ารูปเปลี่ยน โดยไม่ทำสำเนาภาพในประวัติ
- การอัปเกรดเก็บภาพข้อมูลเดิมเป็น BASELINE และไม่สร้างประวัติย้อนหลังที่ไม่มีอยู่จริง ประวัติตำแหน่ง/สถานะเดิมยังอยู่ หน้าเว็บแสดง 100 รุ่นล่าสุดต่อคน ประวัติทั้งหมดอยู่ในฐานข้อมูลและสำเนาสำรอง
- ยังคงไม่มีช่องสถานะในแบบฟอร์มบุคลากร แม่แบบ Excel และวิธีหลายสาขา/หลายใบรับรองใช้แบบเดิมจากรุ่น 1.5

**การตรวจทานนี้เป็นการยืนยันโดยผู้ที่แก้ไขเอง** พร้อมประวัติ ไม่ใช่ขั้นตอนรอผู้อนุมัติอีกบัญชี หากต้องการแยกผู้ขอแก้ไขกับผู้อนุมัติ ต้องเพิ่มกระบวนการอนุมัติแยกต่างหาก

**ผลตรวจรุ่น 1.6:** Node 60 รายการผ่าน ตรวจฐานข้อมูล PostgreSQL ผ่าน PGlite ทั้งติดตั้งใหม่ อัปเกรดซ้ำ การตรวจ revision การปฏิเสธข้ามสิทธิ์ การลบ/กู้คืน การซ่อนเอกสารและใบรับรองของรายการที่ลบ และการย้อนชุด Excel เมื่อผิดพลาด ยังไม่ได้ทดสอบกับบริการจริงของหน่วยงานหรือหน้าจอเบราว์เซอร์จริง

| `dist/api.js` | เรียก RPC ด้วยบัญชีจริง และพฤติกรรมสาธิตที่สอดคล้องกัน |
| `supabase/migrations/20261020_personnel_change_review.sql` | เพิ่ม revision ข้อมูลการลบ ประวัติ สิทธิ์ และ RPC รุ่น 1.6 |
| `supabase/functions/hr-bridge/index.ts` | ปฏิเสธไฟล์ของบุคลากรที่ลบแล้ว และสำรองประวัติใหม่ |
| `apps-script/Code.gs` | สำรองประวัติและงดแจ้งเตือนเอกสารของบุคลากรที่ลบ |

`save_personnel_reviewed(personnel_data, certificate_data, expected_revision, change_reason)` ใช้เพิ่ม/แก้ไขข้อมูลใน transaction เดียว ตรวจ role และเจ้าของข้อมูลจริงบนเซิร์ฟเวอร์ ส่วน `change_personnel_lifecycle(personnel_id, expected_revision, operation, reason)` ใช้ `delete` หรือ `restore` เฉพาะ admin

`save_personnel_with_certificate` เดิมเปลี่ยนเป็นเพิ่มรายการใหม่เท่านั้น เพื่อให้ Excel import เดิมใช้ต่อได้ การแก้ `personnel` ด้วย REST PATCH/INSERT โดยตรงถูกเพิกถอนสิทธิ์จาก authenticated และฟังก์ชันเขียนภายในไม่เปิดให้ client เรียก หน้าเว็บไม่ใช้การเทียบรหัส admin แบบคงที่ ใช้ Auth จริงและรหัสเริ่มต้นจากสคริปต์เพียงครั้งแรก

- ตรวจทั้งสองชีตก่อนยืนยัน และเรียก `import_personnel_bundle(records jsonb)` เพื่อบันทึกทั้งชุดใน transaction เดียว หากใบรับรองหนึ่งใบผิดหรือเลขที่ตำแหน่งชนกัน จะไม่มีข้อมูลของชุดนั้นค้างอยู่
- แม่แบบเก่าที่ไม่มีสาขาหรือใบรับรองยังอ่านได้ รวมถึง CSV บุคลากรเดิม สำหรับ CSV ไม่รองรับใบรับรองหลายใบ ให้ใช้ .xlsx

**ผลตรวจรุ่น 1.5:** Node 52 รายการผ่าน และ PostgreSQL ผ่าน PGlite ตรวจทั้งติดตั้งใหม่ อัปเดตรุ่นเดิม รัน migration ซ้ำ การเชื่อมใบรับรอง การย้อนรายการเมื่อข้อมูลผิด สิทธิ์ admin/บุคลากร และการคงสถานะเดิม ยังต้องตรวจบริการจริงและหน้าจอเบราว์เซอร์ของหน่วยงานตามขั้นตอนตรวจรับ

## สิ่งที่เพิ่มในรุ่น 1.4: ยืนยัน admin ก่อนเปิดรายละเอียด

- หน้าภาพรวมแสดงยอดสรุปและการแจกแจงตามสถานศึกษา วุฒิ และหน่วยงานผู้ออกใบรับรอง เอาตารางรายชื่อผู้ถือใบรับรองออกจากภาพรวม
- ทุกครั้งที่กดข้อมูลจากภาพรวม ระบบขออีเมลและรหัสผ่าน admin แล้วตรวจการเข้าสู่ระบบและบทบาทจากฐานข้อมูลก่อนเปิดหน้าปลายทาง ตัวกรองสถานศึกษา/สถานะเดิมยังอยู่
- ก่อนยืนยัน จะไม่ดาวน์โหลดชุดทะเบียน เอกสาร และใบรับรองทั้งหมดมาไว้ในหน้าภาพรวม เมื่อกลับภาพรวม ระบบล้างรายละเอียดในหน่วยความจำ หน้าต่างแฟ้ม และแถวรายงานที่เตรียมส่งออก และล็อกการเปิดรายละเอียดอีกครั้ง
- การเปิดลิงก์ตรงไปยังหน้ารายชื่อ เอกสาร ใบรับรอง รายงาน และเมนู admin ต้องมีสิทธิ์ก่อน บัญชีบุคลากรยังจัดการได้เฉพาะแฟ้มของตนเองตาม RLS
- บันทึกการยืนยันเปิดข้อมูลที่สำเร็จเป็น `ADMIN_VIEW` พร้อมผู้ใช้งาน เวลา และหมวดข้อมูล ไม่เก็บรหัสผ่านหรือข้อความค้นหาในรายการนี้
- รหัสผ่านและ token ไม่ถูกบันทึกใน localStorage บัญชีจริงสร้างตามขั้นตอนที่ 2 และเปลี่ยนรหัสเริ่มต้นก่อนใช้งาน

**วิธีใช้งาน:** ภาพรวม → เลือกยอดหรือสถานศึกษา → กรอกชื่อผู้ใช้หรืออีเมลเดิมและรหัสผ่าน admin → ยืนยันและเปิดข้อมูล → กลับภาพรวมเพื่อปิดรายละเอียด เมื่อเปิดครั้งถัดไปให้ยืนยันใหม่ บนหน้าที่เปิดดูแล้วสามารถใช้ตัวกรองและเปิดแฟ้มตามสิทธิ์ของรอบการใช้งานนั้นได้

**โหมดสาธิต:** หาก `config.js` ยังไม่มีการเชื่อมต่อจริง ช่องบัญชี admin จะไม่รับรหัสผ่านจริงและมีปุ่ม “ดูข้อมูลสมมติ” สำหรับทดลองการใช้งานเท่านั้น การเปิดข้อมูลสาธิตไม่ใช่การยืนยันตัวตนหรือการป้องกันข้อมูลส่วนบุคคลจริง ห้ามใส่ข้อมูลบุคลากรจริงในโหมดนี้ เมื่อกรอกการเชื่อมต่อจริงแล้ว เว็บเริ่มในสถานะผู้เยี่ยมชมและไม่เปิดให้ใช้ปุ่มข้ามแบบสาธิต หากยังไม่ยืนยันบัญชี หน้าภาพรวมจะแสดงเครื่องหมาย — แทนสถิติจริง

**ขอบเขตการป้องกัน:** หน้าต่างยืนยันเป็นขั้นตอนเปิดดูในเว็บ ส่วนฐานข้อมูลตรวจ Supabase Auth และ RLS ทุกคำขอ `hr_overview()` เป็น security invoker ใช้สิทธิ์ของผู้เรียกและไม่เปิดให้ anon เรียก การเพิ่มรหัสผ่านไม่ใช่การรับรองว่าองค์กรปฏิบัติตาม PDPA ครบถ้วนทั้งระบบ

**ผลตรวจส่วนยืนยันบัญชีในรุ่น 1.4:** การทดสอบ Node 41 รายการผ่าน รวมกรณีรหัสผิด บัญชีไม่ใช่ admin การไม่โหลดทะเบียนก่อนยืนยัน และการล็อกเมื่อกลับภาพรวม ทดสอบ schema/migration แบบรันซ้ำ การนับยอด สิทธิ์บุคลากร/anon และบันทึก admin ด้วย PostgreSQL ผ่าน PGlite แล้ว ยังไม่ได้ทดสอบกับบัญชี Supabase ของหน่วยงานหรือเบราว์เซอร์จริง

## 2. ติดตั้ง Supabase

3. ตรวจ Table Editor มี schools 7 แห่ง, document_types 9 ประเภท, settings 1 แถว และ RLS เปิดทุกตาราง
4. Authentication Settings: ปิด public sign-up เพื่อให้แอดมินสร้างบัญชีเท่านั้น สำหรับโครงการใหม่ที่ต้องสร้างรหัส 123456 ให้ minimum password length อนุญาต 6 ตัวอักษรและกติกาไม่ปฏิเสธรหัสตัวเลขในช่วงสร้างครั้งแรก หลังเปลี่ยนรหัส admin แล้ว ให้ตั้ง minimum อย่างน้อย 8 และกติกาตัวอักษร/ตัวเลขตามนโยบายหน่วยงาน

```bash
node --env-file=.env.bootstrap scripts/bootstrap-admin.mjs
```

สคริปต์สร้าง `admin` / `123456` และตั้ง `must_change_password=true` ผู้ติดตั้งต้องทำขั้นตอน Edge Functions และหน้าเว็บให้ครบก่อนเข้าสู่ระบบครั้งแรก แล้วเปลี่ยนรหัสทันที ไม่อัปโหลด `.env.bootstrap` ขึ้น GitHub หรือวางใน dist สคริปต์ไม่สร้างซ้ำและไม่เปลี่ยนรหัส admin เดิม หากมี admin อยู่แล้วให้ใช้บัญชีนั้นต่อ

6. Authentication → URL Configuration: ตั้ง Site URL ให้ตรง URL เว็บจริง ใช้ HTTPS
7. หลังติดตั้งครบ เข้าด้วย `admin` / `123456` กรอกรหัสเดิมเป็นรหัสปัจจุบัน กำหนดรหัสใหม่และยืนยัน แล้วเข้าสู่ระบบด้วยรหัสใหม่ การปิดหน้าต่างเปลี่ยนรหัสจะไม่เปิดข้อมูลให้
8. เพิ่มหรือนำเข้าบุคลากรก่อน จากนั้น **จัดการบัญชี → เลือกวิทยาลัย → สร้างบัญชี** กำหนด user และ password ให้แต่ละคน ระบบผูก Auth UUID กับบุคลากรให้ ไม่ต้องคัดลอก UUID เอง
9. บัญชีเดิมที่ผูกไว้แล้วใช้ต่อได้ การรีเซ็ตรหัสทำจากแถวของบุคลากร และให้ผู้ใช้เปลี่ยนรหัสหลังเข้าใช้ครั้งแรก ส่วนอีเมลติดต่อแก้ในแบบฟอร์มบุคลากรได้

## 3. สร้าง Google Drive / Sheets / Apps Script

1. ใช้บัญชี Google Workspace ของหน่วยงาน สร้างโฟลเดอร์ `HRVec-Andaman2-Private` ใน My Drive ตั้ง General access = Restricted **อย่าใช้โฟลเดอร์ที่แชร์ทั้งองค์กรหรือสาธารณะ**
2. จด Folder ID จาก URL หลัง `/folders/`
3. สร้าง Google Spreadsheet `HRVec-Andaman2-สำเนาข้อมูล` แบบ Restricted จด ID ระหว่าง `/d/` และ `/edit`
4. สร้าง Apps Script ที่ https://script.google.com วาง `apps-script/Code.gs` ลง Code.gs
5. Project Settings → Show appsscript.json manifest file จากนั้นวาง `apps-script/appsscript.json` ลงไฟล์ manifest
6. Project Settings → Script Properties เพิ่มค่าต่อไปนี้:

| Key | Value |
|---|---|
| DRIVE_FOLDER_ID | โฟลเดอร์ส่วนตัวที่สร้าง |
| SHEET_ID | Spreadsheet ID |
| BRIDGE_SECRET | ความลับสุ่มเดียวกับ Edge Function อย่างน้อย 32 bytes |
| SUPABASE_URL | เช่น https://PROJECT.supabase.co |
| SUPABASE_SERVICE_ROLE_KEY | service_role key ฝั่งเซิร์ฟเวอร์เท่านั้น |

สร้าง BRIDGE_SECRET ด้วย `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` ในเครื่องผู้ดูแล (ใช้ได้บน Windows/macOS/Linux) แล้ววางเฉพาะใน Script Properties และ Supabase Secrets ไม่ใส่ใน config.js, GitHub, ชีต หรือช่องแชต

7. เลือกฟังก์ชัน `testConfiguration` แล้ว Run และอนุญาตสิทธิ์ Drive, Sheets, external requests ตามบัญชีหน่วยงาน ตรวจ Execution log แสดง Configuration OK
8. Deploy → New deployment → Web app → Execute as: Me → Who has access: Anyone แล้ว Deploy คัดลอก URL `/exec` ห้ามใช้ `/dev` ตัว endpoint เปิดรับเครือข่าย แต่ทุกคำสั่งอ่าน/เขียนตรวจ HMAC + timestamp + nonce และรับเฉพาะจาก Edge Function ที่รู้ BRIDGE_SECRET
9. หากผู้ดูแล Workspace ไม่อนุญาต Anyone ต้องให้ผู้ดูแลโดเมนอนุมัติหรือเปลี่ยน integration ไปบริการ server-to-server ที่องค์กรอนุญาต ระบบนี้จะไม่สามารถเรียกผ่านหน้า login ของ Google ได้
10. หลังแก้ Apps Script ให้ Deploy → Manage deployments → Edit → New version → Deploy เพื่อให้ URL เดิมใช้โค้ดใหม่

## 4. ติดตั้ง Supabase Edge Function

ติดตั้ง Node.js รุ่น LTS, Git และ Supabase CLI ตามเอกสารทางการ เปิด terminal ที่โฟลเดอร์โครงการ:

```bash
npx supabase login
npx supabase link --project-ref YOUR_PROJECT_REF
```

สร้าง `.env` ในเครื่องจาก `.env.example` กรอก GAS_URL, BRIDGE_SECRET และ ALLOWED_ORIGINS เช่น:

```text
GAS_URL=https://script.google.com/macros/s/DEPLOYMENT_ID/exec
BRIDGE_SECRET=YOUR_PRIVATE_RANDOM_SECRET
ALLOWED_ORIGINS=https://yourname.github.io,https://your-domain.example
```

Origin มีเฉพาะ scheme + host ไม่มี `/repo/` และไม่มี slash ปิดท้าย ถ้าเปิดผ่าน Sites ให้เพิ่มโดเมน Sites จริงด้วย หากทดสอบ local ให้เพิ่ม `http://localhost:8000` ชั่วคราว

```bash
npx supabase secrets set --env-file .env
npx supabase functions deploy hr-bridge --no-verify-jwt
npx supabase functions deploy hr-accounts --no-verify-jwt
```

`SUPABASE_URL` และ `SUPABASE_SERVICE_ROLE_KEY` เป็น built-in secrets ใน hosted Supabase Edge Function; ตรวจในหน้า Secrets หาก deployment ต่างจากปกติ ห้ามนำ service_role key ใส่ frontend

ไฟล์ config.toml ปิด gateway verify_jwt แต่โค้ดตรวจ access token ด้วย `auth.getUser()` ทุก request ก่อนทำงาน และตรวจ role/owner อีกชั้น ห้ามลบการตรวจเหล่านี้

## 7. วิธีใช้งานประจำวัน

### ผู้ดูแลระบบ

- ข้อมูลบุคลากร → เพิ่มบุคลากร → ระบุเลขที่ตำแหน่ง ชื่อ สถานศึกษา ตำแหน่ง ฝ่าย วิทยฐานะ วันเกิด วันเริ่มงาน จากนั้นสร้างบัญชีในเมนู จัดการบัญชี
- ช่องฝ่ายเลือก **ไม่ระบุฝ่าย** เพื่อเว้นว่างได้ เมื่อเปลี่ยนตำแหน่งเป็น **ผู้อำนวยการ** ระบบจะตั้งช่องฝ่ายเป็นค่าว่างก่อนบันทึก
- ข้อมูลบุคลากร → เลือกสถานศึกษา → แก้ไขในแถวบุคคล → ตรวจค่าเดิม/ใหม่ → ระบุเหตุผล → ติ๊กยืนยัน → ยืนยันบันทึก ตรวจประวัติจากปุ่ม ประวัติ ในแถวเดียวกัน
- ลบในแถวบุคคล → ตรวจชื่อและสถานศึกษา → กรอกเลขที่ตำแหน่งซ้ำ → ระบุเหตุผล → ยืนยันลบ กู้คืนได้จากเมนู รายการที่ลบ ด้วยขั้นตอนยืนยันเดียวกัน
- ใบอนุญาต / ใบเซอร์ → เพิ่ม → เลือกประเภทผู้บริหาร, ทักษะวิชาชีพครู, หรือใบประกอบวิชาชีพครู → ระบุเลขที่ ผู้ออก วันออก/หมดอายุ และเชื่อมเอกสารเจ้าของเดียวกัน
- แฟ้มเอกสาร → อัปโหลด → เลือกบุคลากรและประเภท → ส่งไฟล์ได้สูงสุด 10 ไฟล์ต่อครั้ง ไฟล์ละไม่เกิน 10 MB
- รวมรูปเป็น PDF: เลือก JPEG/PNG/WebP เท่านั้น ติ๊กตัวเลือกรวม ภาพจะถูกย่อและวางทีละหน้า A4 ไม่รวมไฟล์ PDF เดิม
- เอกสารรอตรวจ → เปิดไฟล์เพื่อตรวจ → ตรวจสอบ → อนุมัติหรือส่งกลับพร้อมเหตุผล
- รายงาน → เลือกหนึ่งใน 6 ชุด → กรองสถานศึกษา/ค้นหา → Excel/CSV หรือพิมพ์ A4
- ตั้งค่าระบบ → เปลี่ยนชื่อหน่วยงาน โลโก้ สถานศึกษา ประเภทเอกสาร และอีเมลแจ้งเตือน
- เพิ่มตำแหน่ง/สถานะ/ฝ่าย/วิทยฐานะได้จากตั้งค่า ไม่ลบค่าที่เคยใช้งานเพื่อรักษาประวัติ

### บุคลากร

- เข้าสู่ระบบด้วยบัญชีของตน → ข้อมูลของฉัน → เปิดแฟ้ม → แก้ไขเฉพาะข้อมูลติดต่อและรูป → ตรวจข้อมูล → ระบุเหตุผล → ยืนยัน
- อัปโหลดเอกสารของตน ติดตามสถานะ เมื่อส่งกลับให้แก้ต้นฉบับแล้วอัปโหลดฉบับใหม่ ระบบเก็บฉบับเก่าไว้
- ดูใบรับรองของตนได้ การแก้ทะเบียนราชการและข้อมูลใบรับรองต้องให้ผู้ดูแลดำเนินการ
- บุคลากรไม่เห็นแฟ้มผู้อื่น แม้เปลี่ยน URL/ส่ง request เอง และไม่สามารถอนุมัติเอกสารหรือเปลี่ยนบทบาทตนเอง

ไฟล์ที่ดาวน์โหลดลงเครื่องต้องจัดเก็บตามนโยบายข้อมูลส่วนบุคคลของหน่วยงาน ระบบไม่สร้าง Drive public link

## 8. นำเข้าและรายงาน

หน้า “ข้อมูลบุคลากร” แสดง 2 ช่องทางอย่างชัดเจน

**ช่องทาง 1 กรอกข้อมูลปกติ:** กดกรอกข้อมูลบุคลากร → ระบุเลขที่ตำแหน่ง ชื่อ และสถานศึกษา → เลือกตำแหน่ง ฝ่าย และวิทยฐานะ → ใส่วุฒิสูงสุดและเพิ่มสาขาวิชาทีละรายการ → ใส่วันเกิด วันเริ่มงาน ข้อมูลติดต่อ และภาพ → หากต้องการให้เลือกเพิ่มใบรับรองพร้อมบุคลากรและกรอกชื่อ/ผู้ออก → บันทึก ฟอร์มนี้ไม่มีช่องสถานะ ผู้อำนวยการเว้นฝ่ายได้

**หลายสาขาวิชา:** กด เพิ่มสาขาวิชา สำหรับสาขาที่ 2 เป็นต้นไป เป็นสาขาในระดับวุฒิสูงสุดเดียวกัน เช่น ปริญญาโท สาขาการบริหารการศึกษา และเทคโนโลยีสารสนเทศ หากมีวุฒิหลายระดับ ให้ระบุเฉพาะระดับสูงสุด ส่วนวุฒิอื่นแนบหลักฐานในแฟ้มเอกสาร สาขาเป็นข้อมูลทะเบียนที่ผู้ดูแลบันทึก บุคลากรทั่วไปแก้ได้เฉพาะข้อมูลติดต่อและรูปตามสิทธิ์เดิม

**ช่องทาง 2 นำเข้าจาก Excel:**

1. ดาวน์โหลด `HRVec-Andaman2-Personnel-Template.xlsx` รุ่น 1.5 จากหน้าเว็บ
2. ชีต **บุคลากร** ใช้แถว 1 เป็นหัวคอลัมน์ แถว 2 เป็นต้นไปหนึ่งแถวต่อหนึ่งคน ต้องมีเลขที่ตำแหน่ง ชื่อ-นามสกุล และสถานศึกษา
3. แม่แบบไม่มีคอลัมน์สถานะ บุคลากรใหม่ใช้ ปฏิบัติงาน ไม่ระบุตำแหน่งจะใช้ ครู ช่องฝ่ายเว้นว่างได้
4. สถานศึกษาเลือกจากรายการหรือรหัส 1 ถึง 7 ตำแหน่ง/ฝ่าย/วิทยฐานะต้องตรงค่าที่ตั้งไว้
5. คอลัมน์ **L วุฒิการศึกษาสูงสุด** และ **M สาขาวิชา** หลายสาขาคั่นด้วย `;` เช่น `การบริหารการศึกษา; เทคโนโลยีสารสนเทศ` หรือกด Alt+Enter ในเซลล์เดียวกัน ไม่ใช้ comma เป็นตัวคั่นเพราะอาจเป็นส่วนหนึ่งของชื่อสาขา
6. เปิดชีต **ใบรับรองวิชาชีพ** กรอกหนึ่งแถวต่อหนึ่งใบ ใส่เลขที่ตำแหน่งให้ตรงกับบุคลากรในไฟล์เดียวกัน ไม่ต้องเรียงแถวติดกันก็เชื่อมได้ แต่แนะนำจัดกลุ่มตามเลขที่ตำแหน่งเพื่ออ่านง่าย
7. คนที่มีหลายใบให้เพิ่มแถวและใช้เลขที่ตำแหน่งเดิม **ไม่เพิ่มคอลัมน์ ใบที่ 1/ใบที่ 2** ชื่อแต่ละใบและหน่วยงานผู้ออกต้องแยกกันชัดเจน
8. ใบรับรองต้องกรอกเลขที่ตำแหน่ง ประเภท ชื่อใบรับรอง และหน่วยงานผู้ออก เลขที่ใบรับรอง/วันที่ออก/วันหมดอายุเว้นได้ ใบไม่กำหนดอายุให้เว้นวันหมดอายุว่าง
9. วันที่เป็นวันที่ Excel หรือ `YYYY-MM-DD` ค.ศ. วันหมดอายุต้องไม่ก่อนวันที่ออก ตั้งเลขที่ตำแหน่ง เลขที่ใบรับรอง และโทรศัพท์เป็น Text เพื่อรักษาศูนย์นำหน้า ห้ามใส่สูตรในสองชีตนำเข้า
10. ดูชีต **ตัวอย่าง** และ **ตัวอย่างใบรับรอง** เพื่อเรียนรู้รูปแบบ ระบบไม่ดึงชีตตัวอย่างเข้าอัตโนมัติ ชีต **รายการอ้างอิง** และ **คำแนะนำ** มีรายการที่ใช้ได้และวิธีกรอก
11. บันทึกเป็น `.xlsx` ขนาดไม่เกิน 5 MB ครั้งละไม่เกิน 500 คน / 5,000 ใบ / 100 ใบต่อคน / 20 สาขาต่อคน
12. เว็บ → ข้อมูลบุคลากร → อัปโหลด Excel → ตรวจสอบข้อมูล ระบบแสดงรายชื่อ วุฒิ สาขา จำนวนใบรับรอง และรายการใบรับรองพร้อมผู้ออกก่อนบันทึก
13. หากพบข้อมูลผิด จะระบุชื่อชีตและแถว แก้ไฟล์แล้วเลือกใหม่ หากผ่านทุกแถวจึงกด **ยืนยันบันทึก N คน / M ใบ** ระบบจะบันทึกสองชีตใน transaction เดียว หากข้อผิดพลาดเกิดระหว่างบันทึก ชุดนี้จะถูกย้อนทั้งหมด
14. เปิดแฟ้มตรวจสาขาและใบรับรองอีกครั้ง ระบบเพิ่มเฉพาะบุคลากรใหม่ ไม่เขียนทับบุคลากรเดิม หากเพิ่มใบของคนเดิมให้เปิดแฟ้มในเว็บแล้วเลือก เพิ่มใบรับรอง
15. Excel นำเข้าข้อมูลทะเบียน ไม่อัปโหลดภาพ/PDF หลักฐานให้อัตโนมัติ ให้แนบผ่านแฟ้มเอกสาร แล้วเชื่อมไฟล์กับรายการใบรับรอง
16. หลังนำเข้า ผู้ดูแลเปิดเมนู จัดการบัญชี เลือกวิทยาลัย แล้วสร้าง user/password รายบุคคล ระบบผูกบัญชีให้ การนำเข้า Excel ไม่สร้างรหัสผ่านและไม่เก็บรหัสผ่านในแม่แบบ

ตัวอย่างความสัมพันธ์ของใบรับรองในชีต **ใบรับรองวิชาชีพ**:

| เลขที่ตำแหน่ง | ประเภทใบรับรอง | ชื่อใบรับรองวิชาชีพ | หน่วยงานผู้ออก | เลขที่ใบรับรอง |
| --- | --- | --- | --- | --- |
| 001 | ใบประกอบวิชาชีพผู้บริหาร | ใบอนุญาตผู้บริหารสถานศึกษา | หน่วยงาน A | ADMIN-001 |
| 001 | ใบรับรองทักษะวิชาชีพ | ทักษะเทคโนโลยีดิจิทัล | หน่วยงาน B | VOC-001 |

สองแถวนี้เชื่อมกับบุคลากรเลขที่ตำแหน่ง 001 คนเดียวกัน ไม่ต้องทำบุคลากร 001 ซ้ำในชีต บุคลากร

CSV ยังรองรับหัวคอลัมน์ไทย/อังกฤษเดิมได้ เพิ่ม `education_majors` สำหรับสาขาที่คั่นด้วย `;` แต่รองรับเฉพาะข้อมูลบุคลากร ไม่รองรับหลายใบรับรอง ให้ใช้ .xlsx ตามแม่แบบ เลขที่ตำแหน่งของรายการที่ลบแล้วก็ใช้ซ้ำไม่ได้ ให้กู้คืนรายการเดิมก่อน หากผู้ดูแลสองคนเพิ่มเลขที่ตำแหน่งเดียวกันพร้อมกัน ฐานข้อมูลจะปฏิเสธชุดที่ชนกัน ให้ตรวจรายการล่าสุดก่อนส่งซ้ำ

รายงาน 6 ชุด: ทะเบียนบุคลากร, ความครบถ้วนเอกสาร, ใบอนุญาต/ใบรับรอง, เกษียณอายุ, วุฒิบัตร/อบรม และรายชื่อแยกตามสถานศึกษา รายงานเกษียณแสดงทุกคนเรียงตามวันเกษียณ ผู้ดูแลสามารถกรองปีต่อใน Excel ได้

SheetJS และ jsPDF โหลดจาก CDN ภายนอก หากถูกบล็อก Excel และรวมรูป PDF จะใช้ไม่ได้ แต่ CSV ยังทำงาน ดาวน์โหลดไฟล์ vendor จากแหล่งทางการมาโฮสต์เองก่อนใช้ในเครือข่ายปิดได้ (แก้ script src ใน index.html) โลโก้เริ่มต้นเป็นไฟล์ PNG พื้นหลังโปร่งใสใน dist/logo-transparent.png ซึ่งเตรียมจากโลโก้อ้างอิงของผู้ใช้ หากไฟล์เข้าไม่ถึงมีตัวอักษร HR แทน ผู้ดูแลสามารถเปลี่ยน URL โลโก้เป็นที่เก็บของหน่วยงานได้

## 9. สำรองข้อมูลและอีเมล

- ตั้งค่า → สำรองข้อมูลไป Drive: บันทึก JSON ทุกตารางธุรกิจ พร้อมรายการอ้างอิงไฟล์ ไม่รวม auth.users, รหัสผ่าน, secrets หรือสำเนา binary ไฟล์
- ส่งสำเนาไป Google Sheets: ล้างและเขียนข้อมูลในแท็บที่ชื่อตรงตาราง ไม่กระทบแท็บอื่น รูปโปรไฟล์ถูกละออกเพื่อไม่เกินข้อจำกัดเซลล์ ชีตควรใช้เฉพาะสำเนาระบบ
- ตั้งอีเมล + เปิดแจ้งเตือนในหน้าเว็บ แล้ว Run `installDailyTrigger` ใน Apps Script หนึ่งครั้ง ระบบสำรองและ sync ทุกวันประมาณ 02:00 เวลาไทย และส่งอีเมลสรุปจำนวนรายการรอตรวจ/ใบอนุญาตใกล้หมดอายุ ไม่ส่งข้อมูลส่วนบุคคลในอีเมล
- การแจ้งเตือนเป็นสรุปรายวัน ไม่ใช่ทันทีที่กดอนุมัติ
- ดู Executions ของ Apps Script เมื่อ trigger ล้มเหลว และตรวจ quotas ของบัญชี Google แผนใช้งานจริง
- สำรอง binary ของโฟลเดอร์ Drive เพิ่มต่างหากตามนโยบายองค์กร และตั้ง Supabase database backup/PITR ตามแผนบริการ ผู้ดูแลควรกำหนดระยะเก็บเอง รุ่นนี้ไม่ลบสำรองเก่าอัตโนมัติ
- กู้คืน: หยุดการเขียนระบบ, สำรองสถานะปัจจุบัน, กู้ Supabase backup ไปโครงการทดสอบก่อน, กู้ไฟล์ Drive โดยรักษา/ปรับ file ID ให้ตรง documents, ตรวจบัญชี Auth และ user_id, รัน acceptance test แล้วจึงสลับ config ไประบบที่กู้คืน JSON backup เหมาะใช้ตรวจสอบ/นำเข้าด้วยสคริปต์ผู้ดูแล ไม่ใช่ปุ่มกู้คืนทั้งระบบอัตโนมัติ (เมนู รายการที่ลบ กู้คืนได้เฉพาะบุคลากรที่ soft delete) ห้าม import snapshot ตรงเข้าตารางโดยไม่ตรวจ FK และ Auth UUID
- ล้างแคชในระบบจริงโหลดข้อมูลใหม่เท่านั้น ไม่ลบข้อมูลฐานข้อมูล ในโหมดสาธิตจะถามยืนยันก่อนรีเซ็ต localStorage

### ทดสอบฐานข้อมูลแบบแยกจากข้อมูลจริง

ชุดทดสอบปกติใช้ `npm run check` และ `npm test` หากต้องการทดสอบ PostgreSQL/RLS แบบเดียวกับที่ตรวจชุดส่งมอบ ให้ติดตั้งเครื่องมือทดสอบเพิ่มเติมในเครื่องพัฒนา:

```bash
npm install --no-save @electric-sql/pglite@0.3.14
node tests/personnel-db.mjs
node tests/accounts-db.mjs
```

สคริปต์สร้างฐานข้อมูลในหน่วยความจำ จำลอง Supabase Auth และไม่เชื่อมฐานข้อมูลหน่วยงาน ส่วน `tests/live-rls.mjs` ใช้เฉพาะโครงการทดสอบที่ตั้งบัญชี A/B และตัวแปรแวดล้อมเองตามคำอธิบายในไฟล์

## 10. การตรวจรับก่อนเปิดใช้งานจริง

รุ่น 1.2 ให้ตรวจเพิ่มดังนี้: บันทึกบุคลากรพร้อมวุฒิและใบรับรอง → เปิดแฟ้มยืนยันหน่วยงานผู้ออก → เพิ่มใบรับรองอีกใบให้คนเดิม → ยอดใบรับรองเพิ่ม 1 แต่ยอดผู้ถือไม่เพิ่ม → คลิกสถานศึกษาและตรวจรายชื่อ → กรองใบรับรองตามหน่วยงานพร้อมสถานะ → ทดลองใบรับรองที่ไม่ระบุหมดอายุ → ทดลองวันหมดอายุก่อนวันออกและตรวจว่าไม่มีข้อมูลบันทึกค้าง → นำเข้า Excel คอลัมน์ L และ M พร้อมใบรับรองหลายใบ แล้วตรวจวุฒิ สาขา และหน่วยงานผู้ออกในแฟ้มและรายงาน


1. สร้าง admin ด้วย bootstrap เปลี่ยนรหัสเริ่มต้น แล้วสร้างบัญชีบุคลากร A/B จากเมนูจัดการบัญชี
2. Admin เห็นทุกแห่ง A เห็นเฉพาะตน B เห็นเฉพาะตน; ผู้ไม่ login ไม่อ่านตารางจริง
3. ลองแก้ contact ของ A สำเร็จ แต่ส่ง request เปลี่ยน status/position/user_id และ profiles.role ต้องถูกปฏิเสธ
4. A อัปโหลด PDF/JPEG/PNG/WebP, รูปหลายใบรวม PDF; ดู Drive ว่าไม่สาธารณะ
5. ลองปลอม personnel_id เป็น B และดาวน์โหลดเอกสาร B ด้วย token A ต้อง 403
6. ส่งไฟล์ MIME ปลอม, >10 MB, unsigned GAS request, HMAC ถูกแก้, replay nonce ต้องถูกปฏิเสธ
7. Admin ส่งกลับพร้อมเหตุผล A เห็นเหตุผลและอัปโหลดฉบับใหม่ Admin อนุมัติแล้วความครบถ้วนเปลี่ยน การอัปโหลดไฟล์ชนิดเดิมซ้ำไม่เพิ่มคะแนน
8. เปลี่ยนตำแหน่ง/ฝ่ายแล้วตรวจ status_history และ audit_log การแก้ฟอร์มต้องไม่เปลี่ยนสถานะเดิมโดยอัตโนมัติ
9. ใบรับรองที่เลือกหลักฐานคนอื่นหรือหมดอายุก่อนวันออกต้องถูกปฏิเสธ
10. นำเข้าไฟล์วันที่ผิด/เลขที่ตำแหน่งซ้ำ/โทรมีศูนย์นำหน้า และทดสอบสูตรอันตรายเป็นข้อความทั้ง CSV และ Sheets
11. ส่งออกทั้ง 6 รายงาน ตรวจภาษาไทย เลขศูนย์นำหน้า และ Print Preview A4 บน Chrome/Edge
12. เรียก backup/sync แล้วเปิด Google Drive/Sheets ตรวจข้อมูลครบ Run dailyMaintenance ตรวจอีเมล
13. Logout แล้วข้อมูลจริงหายจากหน้าเว็บ การ refresh ต้อง login ใหม่ (token เก็บในหน่วยความจำ ไม่เก็บ localStorage)
14. ทดสอบมือถือจริงและการโหลด CDN ในเครือข่ายองค์กร
15. กรองสถานศึกษาแล้วแก้ไขจากแถวบุคคล ตรวจว่าไม่มีข้อมูลเปลี่ยนก่อนยืนยัน และปุ่มย้อนกลับคงร่างที่กรอกไว้
16. เปิดบุคลากรคนเดียวกันในสองบัญชี admin บันทึกจากบัญชีแรกแล้วลองบันทึก/ลบจากหน้าจอเดิมของอีกบัญชี ต้องแจ้งโหลดใหม่และไม่มีการเขียนทับ
17. ลองยืนยันลบด้วยเลขที่ตำแหน่งผิด/ไม่ระบุเหตุผล ต้องยังลบไม่ได้ ลบถูกต้องแล้วตรวจยอด รายงาน และคิวเอกสารลดลง พร้อมประวัติผู้ดำเนินการ
18. บัญชีเจ้าของที่ถูกลบต้องไม่อ่านแฟ้ม/เอกสารเดิม admin ต้องดาวน์โหลดหรือเพิ่มเอกสารให้รายการที่ลบไม่ได้ แต่ยังอ่านเหตุผลและประวัติในรายการที่ลบได้
19. กู้คืนจากรายการที่ลบ ตรวจว่า UUID และเอกสาร/ใบรับรองเดิมกลับมาครบ ภาพรวมกลับมานับ และมีประวัติ RESTORE
20. บุคลากรมีปุ่มแก้ไข ขอลบ และประวัติของตน ไม่เห็นเมนูจัดการบัญชี/รายการที่ลบ และเรียก RPC ลบตรงหรือแก้ทะเบียนผู้อื่นไม่ได้
21. เข้าด้วยรหัสเริ่มต้นแล้วลองอ่านตาราง/เรียก RPC/อัปโหลดตรง ต้องถูกปฏิเสธจนเปลี่ยนรหัส
22. หลังรีเซ็ตหรือพักบัญชี ใช้ JWT เดิมและ session_id เดิมซ้ำต้องไม่ผ่าน แม้มีการ refresh
23. ส่งคำขอลบผิดเจ้าของ/ซ้ำต้องไม่ผ่าน แอดมินอนุมัติถูกคนแล้วจึงลบ และคำขอที่ข้อมูลเปลี่ยนระหว่างรอพิจารณาต้องให้ส่งใหม่

รันทดสอบ RLS เพิ่มด้วย `node tests/live-rls.mjs` หลังตั้ง environment variables ตามหัวไฟล์ ใช้บัญชีทดสอบเท่านั้น สคริปต์ทดสอบการปฏิเสธคำสั่งที่ไม่ควรอนุญาต

## 13. ใช้งานบัญชีและตรวจคำขอลบ

แอดมิน: เข้าสู่ระบบ → จัดการบัญชี → เลือกวิทยาลัย → สร้างบัญชี → กำหนดชื่อผู้ใช้และรหัสผ่านสองช่อง → ตรวจบุคคลและยืนยัน ส่งมอบรหัสให้เจ้าของตามช่องทางของหน่วยงาน หากลืมรหัส เลือก รีเซ็ตรหัสผ่าน กำหนดรหัสใหม่ แล้วแจ้งให้เจ้าของเปลี่ยนอีกครั้งหลังเข้าใช้

บุคลากร: เข้าด้วยบัญชีที่ได้รับ → เปลี่ยนรหัสครั้งแรก → ข้อมูลของฉัน → แก้ไขข้อมูลติดต่อ/รูป → ตรวจค่าเดิม/ใหม่และเหตุผล → ยืนยัน ประวัติของฉันอ่านได้เฉพาะรายการของตน

คำขอลบ: บุคลากรกด ขอลบข้อมูล ยืนยันเลขที่ตำแหน่งและเหตุผล → เมนูคำขอลบข้อมูลแสดงผลรอพิจารณา → แอดมินตรวจชื่อ วิทยาลัย เหตุผล และรุ่นข้อมูล → อนุมัติหรือไม่อนุมัติพร้อมเหตุผล อนุมัติแล้วข้อมูลไปอยู่รายการที่ลบและกู้คืนได้ หากข้อมูลเปลี่ยนระหว่างรอ ให้ไม่อนุมัติและให้ผู้ขอส่งใหม่

การตัดสิทธิ์เซสชันมีผลกับคำขออ่าน/เขียนครั้งถัดไป ข้อมูลที่เคยแสดงบนหน้าจอหรือดาวน์โหลดไปแล้วไม่ได้ถูกเรียกคืนย้อนหลัง ระบบนี้ยังใช้สองบทบาท admin รวมทุกวิทยาลัย และบุคลากรเฉพาะตน
